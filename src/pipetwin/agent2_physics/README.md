По новому запросу пользователя выполнена [диагностика причин слабого cold-переноса](CASE2_DIAGNOSIS.md),
включая проверку пользы поздних обучающих ВТД на отдельной известной магистрали.

Последний завершённый этап: [поиск для кейса 2](CASE2_SEARCH_RESULTS.md) по
[заранее записанному протоколу](CASE2_SEARCH_PROTOCOL.md). Нормировка потери
и поправки по рельефу проверены на общих фолдах; подтверждённого существенного
выигрыша нет. Новые опции экспериментальные, значения по умолчанию сохранены.

## Какую задачу решаем

- Кейс 1: простой участок `1250022871`, прогноз ВТД на **2023-12-01**, прошлое ВТД **2022-07-06**.
- Кейс 2: простой участок `1250009583`, прогноз ВТД на **2022-07-01**, прошлого ВТД нет.
- Все источники, train-метки и обучаемые преобразования ограничиваются отдельным cutoff каждого кейса. В кейсе 2 **запрещены ВТД 2022-07-06 и все кампании 2023**, включая другие трубы и fitted-модели из кейса 1.

Ваш ранее написанный E03 находится в коммите `659c251cba1f8e3e73c232758487099793537571` ветки `codex/e02-physical-features`. Перенесите подходящий код в этот пакет и адаптируйте к общему интерфейсу. Не заменяйте им основные `sources.py`, `features.py`, `models/physics.py` или `pipeline.py`: они уже имеют другой общий API и более широкую область применения.

## Что реализовать

1. `constant_rate`: робастно калибруемая неотрицательная скорость как контроль.
2. `positive_rate`: ежедневная положительная скорость по нормализованному режиму с регуляризацией и явным интегралом потери.
3. `hybrid_residual`: физическая компонента и сильно регуляризованная знаковая ML-поправка, обученная только на train.
4. `hybrid_scale`: имеющуюся положительную масштабную поправку добавить после обязательных моделей и тестов, если остаётся время.

Все обязательные модели должны иметь режимы `between` и `cold` с раздельным обучением. Для cold начальное состояние задаётся паспортным номиналом согласованной эпохи; модель не получает историю ВТД. Для between без наблюдаемого якоря используется переданный общим конвейером `fallback_mm`.

Не расширяйте задачу до GEV, GAMLSS, GP/гамма-процесса, оценки шума прибора, собственного стекинга или большого подбора гиперпараметров. Повторную реализацию общего Random Forest не нужно делать отдельным основным кандидатом: он уже есть в общей системе.

## Порядок работы

1. Создайте новую ветку `codex/agent2-physics-contract-v1` от опубликованного коммита основной ветки с этим контрактом. Зафиксируйте фактический SHA базы в `RESULTS.md`.
2. Реализуйте фабрику в `adapter.py`, вынесите модели/интегрирование в дополнительные модули внутри этой папки. Публичная сигнатура уже задана; общий конвейер подключит её после проверки.
3. Напишите содержательные синтетические тесты из списка в контракте. Можно начинать сразу: готовые реальные frame/exposure для нового контракта ещё готовит основной агент.
4. Получив общие данные и сохранённые фолды, сравните обязательные модели с предоставленными baseline на одинаковых ключах. Не используйте старые 355 строк и собственные пять фолдов как замену общей проверке.
5. Запустите ограниченный набор `observed-only` / `train-median`, фиксированные параметры и seed. Не выбирайте настройки по запрещённым будущим кампаниям или по скрытой цели.
6. В `RESULTS.md` укажите выполненные проверки, версии, время, метрики/ограничения и путь к прогнозам. Сохраняйте отдельные коммиты проверенных частей. Основной агент выполнит интеграцию и общий экспорт.
